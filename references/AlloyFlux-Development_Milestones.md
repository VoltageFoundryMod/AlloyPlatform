    ⓵ **The engine does not fit at the stock clock.** Measured `690us/666us, headroom −3.6%, slow-blk climbing ~1400/s` — i.e. _every_ block late, ~70 DMA underruns/sec, continuous crackle.     ⓶ **The engine runs hot enough to clip the DAC.** Peak 1.336 with output level already at 0.5 — ~2.5 dB over full scale — and `AudioDriver::toWire()` hard-clamps, so **0.11 % of samples (≈106/sec)** became hard discontinuities. That is a _second_, independent crackle source, distinct from the underruns, and the host harness now counts it. Fixed with a master `SoftClip` at the module's output edge in `renderAudio()` (`COIL_OUTPUT_SOFTCLIP`, default on) — measured 1.336 → 0.893 peak, 1056 → **0** clipped samples. It complements `scale` rather than replacing it — `Log` handles multiplicative ranges but cannot be used where a range crosses zero, which is exactly the dB case. Round-trip verified exact (0 CC steps of error) for every parameter using it.
    - **`revdecay` → `skew: 0.5`.** It is a tank feedback coefficient and reverb time goes as `1/ln(fb)`, so linear gave 0.28–2.5 s over the first 80 % of travel and 2.5 s–∞ in the last 20 %. Modelled against `T60 = D·ln(0.001)/ln(fb)` with D ≈ 65 ms (mean of ReverbSc's eight tank loops at 48 kHz); now roughly geometric, ~1.3–1.4× per 10 % of travel.
    - **`echofb` → `max` 1.5 → 1.2, no skew.** The model said skew was the _wrong_ tool here: everything above unity blooms to the SoftClip ceiling and sounds much the same, so the top third was already indistinguishable and skewing would have grown it to 40 %.   - [x] 63f-ab. **The echo A/B — both M63f DSP risks measured and discharged.** `make coil-ab` / `make coil-ab-sweep`, source in `modules/alloycoil/test/echo_ab.cpp`. Done as an offline harness with an inline FFT rather than a swept sine into Rack's spectrum analyser: the answer wanted is a number that can be re-checked in a minute and can gate a later change, not an impression. It drives `EchoDelay` directly — no string, no reverb, no feedback loop — so nothing else can colour the result, and it takes `COIL_ECHO_MAX_S` from the engine header so the buffer under test is the size the firmware actually builds.

    A switch was added for the measurement: **`COIL_ECHO_ANTIALIAS`**, purely so the filter can be compared against its own absence. Turning it off in a shipping build is not a trade-off, it is a bug, and the header says so.

    **Risk 1 — fold-down. The anti-alias filter works and is load-bearing.** Fold-down level for a 0 dBFS input, filter off → on: 7 kHz→5 kHz −30.5→−49.9 dB; 9 kHz→3 kHz −15.1→−44.9; **11 kHz→1 kHz −3.1→−41.1**; 13 kHz→1 kHz −3.1→−50.2; 17 kHz→5 kHz −30.5→−99.0. Without it the fold-down is as loud as the input, at 1 kHz, exactly where the loop's 800 Hz bandpass passes it through untouched — the risk was entirely real.

    **A second artifact turned up that the filter cannot touch, and it would have been easy to misread as a failure of the first:** _reconstruction imaging_ from the linear interpolator on the way back up. A 5 kHz input produces a 7 kHz image (12000 − 5000) at −43 dB, against −71 dB for the same spur in the ÷1 reference build. Not aliasing, not fixable by an input filter; would need a better reconstruction filter. At −43 dB in a tape-ish echo it reads as character. Measured rather than assumed, which is the difference that matters.

    **Risk 2 — quantiser noise. int16 costs 0.0–0.1 dB and is therefore free.** SNR with a −40 dBFS tone circulating at 0.95 feedback: ÷1 float 38.1 dB, ÷4 float 37.6, ÷4 int16 37.6. The floor is set by `SoftClip`'s intermodulation inside the loop, not by the quantiser. With over-unity feedback and true silence in, output is bit-exact zero in every build — **the quantiser does not bootstrap itself.** That is the 8× memory reduction vindicated: 750.2 KiB → 93.9 KiB per channel for no audible cost, which is the whole reason Alloy Coil fits at all.

    **Two changes fell out of the numbers, both applied:**
    - **`COIL_ECHO_NOISE_SHAPE` default 1 → 0.** Error feedback is the textbook improvement on a quantiser and it bought nothing here (37.5 vs 37.6 dB). What it cost was silence: the error term keeps the quantiser dithering around zero, leaving a permanent −118.9 dBFS floor where plain truncation decays to bit-exact zero. Inaudible alone — but this echo allows feedback past unity, which amplifies that floor at ~1.7 dB/s. Trading a measurable "never truly silent" for an unmeasurable improvement is the wrong way round.
    - **Anti-alias cutoff 0.35 → 0.25 × the decimated rate** (4200 → 3000 Hz). Another 12 dB of rejection: the 11 kHz worst case went −41.1 → **−53.2 dB**, 13 kHz → −62.3. Nearly free, because the loop's own bandpass is at 800 Hz / 12 dB/oct and has already taken 23 dB out by 3 kHz — there is very little real echo content in the band given away. SNR unchanged at 37.6 dB.

    ⚠️ **One measurement trap, recorded because it produced a confusing result first:** a single-sample impulse is a useless stimulus for a decimated path. The decimator only samples every kDecim-th frame, so a one-sample impulse is simply never seen — three times out of four at ÷4. With the anti-alias filter on it smears across enough samples to get through, so the impulse "works"; with the filter off it vanishes entirely and the echo reads as silent. The harness primes with a 10 ms raised-cosine burst instead, which survives both.

It now has a single stacking decision, taken in `App.svelte` and shared by `PanelView`, the utility rail and `ConnectionBar` — they must switch together or the panel stacks into a column while the rail is still taking a third of it. ⚠️ **It started as a fixed 820 px breakpoint and that was wrong twice over, caught on a real phone.** It was a guess rather than a measurement, and one number cannot serve two modules: the frame only scrolls once the fit falls under `MIN_SCALE`, which is 1178 px for AlloyFlux's 1900-unit stage and 651 px for Alloy Coil's 1050-unit one. 820 was right for neither, and it left AlloyFlux scrolling horizontally between 820 and 1178 — which is exactly where **a phone in landscape** sits, at ~844 px. `shouldStack(viewportW, stageW)` derives it instead, so the rule is "stack precisely when the panel could not be shown whole", true per module by construction; Coil at 844 px fits at 0.80 and correctly stays zoomed. It reads the **viewport**, never an element: the rail gives its width back when the layout stacks, so measuring the frame feeds back on itself and oscillates at one particular window size.

    **The stage stops being a stage below the breakpoint, and that reverses a deliberate decision.** Zooming a fixed composition is right wherever there is room to zoom into, and on a phone there is not: `MIN_SCALE` against a 1700-unit stage is still 1054 px, so a 390 px screen does not get a smaller panel — it gets the same panel behind a horizontal scrollbar, pan-and-hunt, every knob too small to grab. **Landscape does not rescue it either**, which was the first draft's assumption: the stage is 2:1 and a phone on its side is 2.16:1 but only 844 px long, so the fit lands near 26 % either way. So below 820 px the sections stack into one column at _native_ size and the page scrolls vertically, which is the one thing a phone is good at.

    ⚠️ **A span of 5 in a one-column grid does not clamp** — it invents four implicit columns and puts the section in a row five screens wide. `grid-column: 1 / -1` has to reach into `PanelSection`'s scope with `:global()`; the spans themselves stay authored in `panelLayout.ts`, where they mean something at every other width.

    **The rail becomes a bottom sheet**, which reverses the other desktop rule. "The rail shrinks the control surface instead of covering it" is the right trade wherever there is width to give, and at 390 px the rail's own 300 px floor is most of the viewport — giving ground would leave nothing to give it to. It sits _above_ the pinned bottom drawers rather than under them, via a `--dock-h` custom property publishing the height `.dock-spacer` already measures, because a media query cannot see a JS value. The connection bar already wrapped between sections but not within one, so a long port name ("Alloy Flux (loopMIDI Port 1)") dragged the row past the screen edge; it now wraps inside a section and the port `select` is capped at 46vw.

    Touch itself needed nothing: `Knob.svelte` was already on pointer events with `setPointerCapture` and `touch-action: none`, and `index.html` already carries the viewport meta without which none of the above would fire.

    **Not done:** nobody has looked at it. `make web-dev` plus DevTools device emulation settles most of it with no hardware; a real phone settles the rest — in particular whether one-column-at-native-size scrolls to a sensible length or turns the panel into a mile of knobs.

  - [ ] 78e. **Wireless firmware update — over WiFi, deliberately not BLE, and deferred.** BLE at ~1–5 KB/s is minutes for a ~350 KB image; the core ships `PicoOTA`, `ArduinoOTA` and `HTTPUpdateServer` for the sane version. Two hard constraints. A flash write **stops audio** — `EEPROM.commit()` already parks core 1 for ~10 ms and a whole image is far worse — so OTA has to be an explicit mode that mutes and stops the audio driver first, never something that can begin while someone is playing. And **the OTA partition layout has to be reserved now**, because it cannot be retrofitted onto modules already in the field. The wireless image is at 14.2 % of 4 MB flash, so there is room to spare; reserve it before the first board ships, not before the first BLE packet.

    A second WiFi idea worth recording rather than doing: SoftAP + `WebServer` + LittleFS serving the Controller off the module itself. It is the only path that reaches iOS (plain HTTP, none of the blocked APIs) and it solves Controller distribution as well — but WiFi costs far more RAM and power than BLE, and on the measured numbers above that is a conversation AlloyFlux would have with only 15 % of its SRAM left.

  - [ ] 78f. **Does Alloy Coil get wireless? Measured, and deliberately deferred until AlloyFlux-W is on a bench.** M78 ruled it out on an estimate; the estimate was low, and the real answer is more interesting than "no". Every number below is from a build, not arithmetic.

    **BLE costs the same on both modules — +80 820 B on Coil against +80 724 B on AlloyFlux.** It is BTstack and the cyw43 driver, not anything about the module, so no version of this gets cheaper by writing better code. The echo buffer is the only lever of comparable size, and it is exactly **48 000 B per second** (12 kHz × int16 × stereo), perfectly linear:

    | echo | decimation   | wireless Coil RAM | heap left                 |
    | ---- | ------------ | ----------------- | ------------------------- |
    | 4 s  | /4 _(today)_ | 106.5 %           | link fails, over by 34 KB |
    | 3 s  | /4           | 510 424 (97.4 %)  | 13.9 KB                   |
    | 4 s  | /6           | 494 424 (94.3 %)  | 29.9 KB                   |
    | 5 s  | /8           | 486 424 (92.8 %)  | 37.9 KB                   |
    | 2 s  | /4           | 462 424 (88.2 %)  | 61.9 KB                   |
    | 4 s  | /8           | 462 424 (88.2 %)  | 61.9 KB                   |

    **That "free" column is heap, and only heap — the stacks are not in it.** `memmap_default.ld` puts both core stacks in SCRATCH*X / SCRATCH_Y, 4 KB each at 0x20080000 / 0x20081000, outside the RAM region entirely; `.heap` then runs from `__bss_end__` to the end of RAM. So the percentage is not competing with the stacks, and what is left is exactly what the Arduino BLE wrapper allocates from. BTstack itself uses static pools (`btstack_memory.c`, the `MAX_NR**` defines), which is precisely why its 79 KB lands in the *static\* figure rather than the heap — the wrapper's own heap use is a few `strdup`s, three small structs and some `std::list` nodes. `rp2040.getFreeHeap()` is the instrument to confirm that on a live board rather than reasoning about it.

    **The two 88.2 % rows cost exactly the same, and that is the finding worth keeping.** The trade is not "how much echo do you give up", it is **length or bandwidth**. `COIL_ECHO_DECIMATION` is already a build flag, so trying either is free.

    ⚠️ **If decimation is the lever, the risk is not the anti-alias cutoff — it is reconstruction imaging.** The cutoff is `decim_rate × 0.25` (`EchoDelay.h`), so /4 gives 3000 Hz and /8 gives 1500 Hz — and M63i _lowered_ that ratio in the first place because the loop's own 800 Hz / 12 dB-per-octave bandpass has already taken 23 dB out by 3 kHz. There is very little real echo content up there to lose. What M63f-ab did find, and explicitly could **not** filter away, is the linear interpolator's image on the way back up: at /4 a 5 kHz input images at 7 kHz (12000 − 5000) at −43 dB, which reads as character. Decimating further drags that image _down toward_ the content — at /8 a 2 kHz input images at 4 kHz. That is the number which actually decides this, and `make coil-ab` / `make coil-ab-sweep` measures it in a minute; it is the exact question that harness was built for. **/6 at 4 s is the conservative first try**: it keeps the full echo length and moves the image to 8000 − f rather than 6000 − f.

    ✅ **Measured on hardware, and the answer is neither RAM nor CPU — it was a burst.** With BLE connected and a control moving: slow blocks ~124/s without the radio against ~140/s with it (+13 %, i.e. almost nothing), headroom unchanged at ~10 % either way — but **DMA underruns went from ~0/s to ~5/s**, audible as evenly spaced clicks at the feedback rate. Same slow blocks, suddenly draining the cushion. The cause was `bleSendCC()` emitting **one BLE packet per changed CC**: the 250 ms feedback diff fires with every CC that moved, so dragging a control produced a burst of separate GATT notifications, and on a module with 10 % block headroom that burst was enough. Coalescing them into one packet per control tick removes the burst rather than the work — a BLE MIDI packet carries several messages, which is what the format is for. **The lesson generalises: on a module this tight, what breaks the audio is not average cost but bunching.**

    ⚠️ **RAM is probably not the binding constraint anyway — CPU is.** Coil has **13.2 % headroom** (578 µs against a 666 µs budget) and only reached it after M63i fought it down from 942 µs; AlloyFlux has ~64 %. BLE adds core-0 IRQ work and cyw43 PIO/DMA traffic contending on the crossbar with core 1's reads of a 187 KB echo buffer in SRAM. A fifth of the margin to absorb an unknown is the real question here, and no amount of echo shortening answers it. Decimating further does at least cut the echo loop's own rate, so it is a small CPU _win_ rather than another cost.

    ⚠️ One second-order item if this ever proceeds: Coil runs at **192 MHz**, and the core's `init_cyw43_wifi()` only drops the cyw43 PIO clock divisor from /2 to /4 at `clk_sys >= 250 MHz`. 192 MHz would therefore run the radio's SPI bus at /2, i.e. 28 % above what a stock Pico W does. Probably fine, unverified, and trivially testable by forcing the divisor.

    ✅ **The candidate build now exists and is flashable: `env:alloycoil_w`, 4 s at /6, measured at 494 424 B (94.3 %).** `make firmware MODULE=alloycoil WIRELESS=1`. It is in `FW_ENVS` so it keeps compiling. **Pairing is a 3 s hold on WARP** — `BUTTON_1` / SW2, the *same physical switch* AlloyFlux calls MODE, so the gesture is in the same place whichever firmware the shared PCB is running. Two earlier attempts were worse: advertising at boot (a placeholder — wrong default for something living in a rack on a stage) and then a hold on SHIFT, chosen because WARP was momentary and holding it *was* the warp effect. **Making WARP a toggle is what freed it**: the state change is an edge rather than a level, so the button can be held. ⚠️ That toggle first landed on the *press* edge, which meant the hold had already flipped warp by the time it fired and the handler had to revert it — three audible seconds of warp on every pairing attempt. It now lands on the **release** edge, where a press that turns into a hold can be marked consumed (`CoilButtonState::warpConsumed`) and suppressed outright, which is the same thing AlloyFlux's `sModeConsumed` does. A press edge cannot distinguish a tap from the start of a hold; a release edge does not have to. The cost is that a tap toggles when you let go. Coil's LEDs are not firmware-driven, so there is no panel feedback; the console prints `shift held -> ble <state>`. This is still a bench build to answer the CPU question with, not a decision.

    ✅ **ANSWERED ON HARDWARE, and the answer is that the radio costs ~147 µs per block.** Alloy Coil, idle, nothing connected, `sys clock` confirmed at 192 MHz, `smoother` at 32 frames, `set/step 0`: **585 µs wired, ~732 µs wireless, against a 666 µs budget.** Coil had ~81 µs of headroom and BLE wants ~147, so the wireless build at 192 MHz is not marginal — it is unusable, with every block late and underruns running continuously.

    **The decisive reading was `ble poll 0`**, a runtime switch that stops `bleMidi_update()` doing any work while leaving the radio and BTstack up: **738 µs → 727 µs, i.e. nothing.** So none of the cost is MIDI work, packet framing or polling — it is background contention for bus and XIP cache from BTstack and the cyw43 driver, present whether the radio is idle, advertising or connected. Nothing in `ble_midi.cpp` can reduce it, which is why the fix is headroom rather than code.

    ⚠️ **The same ~147 µs applies to AlloyFlux-W**, which simply never noticed: it renders a block in ~240 µs against the same 666 µs budget, so the radio takes a slice of a 64 % margin instead of overrunning a 12 % one. The cost is a property of the platform, not of either engine.

    **`env:alloycoil_w` therefore runs at 230.4 MHz** — the next exact I2S divider up (75.0, ×256 = 19200), +20 %, which turns ~732 µs into ~610 µs and +8.4 % headroom. Thin, and honest about being thin; `ECHO_DECIM=8` is the next lever if it is not enough, and it costs echo bandwidth rather than length. ⚠️ The core only drops the cyw43 PIO SPI divisor from /2 to /4 at ≥ 250 MHz, so this runs the radio bus ~20 % faster than the proven 192 MHz — if BLE turns flaky, add `-DCYW43_PIO_CLOCK_DIV_INT=4` before blaming the clock.

    ⚠️ **Two bugs found on the way there, both mine, both worth the entry.** ⓵ The `cyw43_wifi_pm()` radio probe from M78b brought the *WiFi* interface up on a Bluetooth-only module — `cyw43_poll` non-NULL, continuous driver polling, PM2 powersave — and cost **~595 → ~1036 µs**. Reverted; see 78b. ⓶ `canSendCB()` re-armed the can-send callback after a *failed* `att_server_notify()`, which is an unbounded IRQ storm: btstack calls straight back, the same packet fails, the callback re-registers. The retry now waits for the 128 Hz tick. Between them they accounted for ~500 µs of the ~1226 µs that was first reported.

    ✅ **Alloy Coil runs wireless, cleanly. It needed two unrelated fixes, and confusing them cost a session.**

    ⓵ **The average** — at 192 MHz the wireless block ran ~732 µs against 666 µs. A permanent deficit; no amount of buffering survives one. Fixed by 230.4 MHz, the next exact I2S divider (75.0, ×256 = 19200), which brings it to ~605 µs and ~9 % headroom.

    ⓶ **The jitter** — blocks that land at ~605 µs occasionally arrive at ~710 µs when BLE traffic moves, and the I2S queue was only **2.7 ms** deep (`kNumBuffers = 4`). Deep enough for a long control tick, not for a cyw43 PIO-SPI DMA stall. `-DAUDIO_DMA_BUFFERS=8` makes it 5.3 ms. **Underruns went from climbing at 10–160/s to flat at 3**, with slow blocks still happening and now harmless.

    ⚠️ **The diagnostic that mattered was a pair of failures.** `smooth 64` and `ECHO_DECIM=8` both changed nothing — and that is what proved the spikes were a *stall* rather than *work*, because making the DSP cheaper cannot fix being held off the bus. Two negative results were worth more than any of the positive theories that preceded them. A deeper queue does not make a block faster; it gives the DAC something to play while core 1 is blocked.

    **Latency is the price**, so the shipped depth is the smallest one measured to work rather than the one with the most margin: 4 (2.7 ms) clicks, 8 (5.3 ms) is clean, 12 (8.0 ms) is clean. 8 it is — the true minimum lies somewhere in 5..8 and was not worth the flashes to find. 5.3 ms of output delay is something a resonator and an echo can afford and a gate-responsive voice might not. `alloyflux_w` deliberately stays at the 2.7 ms default — it has ~64 % headroom, its spikes never overrun, and adding latency to a voice without evidence would be the wrong trade. `DMA_BUF=n` is the knob if that ever changes.

    ✅ **Decided, and the answer is yes — Alloy Coil ships wireless.** With M81's hot path moved into RAM it runs at **490 µs against 666, 26.9 % headroom, underruns flat, with BLE up and a phone connected.** That is more margin than the *wired* module ever had (12.2 %), so the radio is no longer the thing constraining it.

    What it took, and each part is load-bearing: **`/6` echo decimation** for RAM (BLE costs 79 KB and Coil had 46 KB), **230.4 MHz** for CPU, **8 I2S buffers** for the jitter a radio causes, and **M81's RAM move** for the layout sensitivity that made every earlier measurement untrustworthy. The overclock stays for now even though 192 MHz would probably fit: the ADC mux, the pot reads and the CV jacks are still to come, and it is better to find their cost against real margin than against none.

    **So: do not decide this now.** Bring up AlloyFlux-W (78b) and measure what BLE does to `gAudioBudgetUs` and the DMA underflow counter on a module with 64 % headroom to spare. If the answer is "nothing measurable", Coil becomes a real conversation and /6 at 4 s is the first thing to A/B. If BLE costs even 5 % of a block, Coil is answered without anyone giving up a second of echo.

  - [x] 81. **Alloy Coil's block time depends on where its code lands in flash — ~300 bytes cost 172 µs.** Found the hard way during M78f, and it is the most important thing that came out of it: this module is not merely close to its budget, it is *unstable* against unrelated change.

    **Measured by bisect, on hardware, wired build, same clock and same patch throughout:**

    | build                                   | block   |
    | --------------------------------------- | ------- |
    | pre-session HEAD                        | 585 µs  |
    | + the M78a MIDI-core refactor           | 592 µs  |
    | + everything else from M78              | **767 µs** |
    | …minus two diagnostic counters          | 595 µs  |

    The two counters were a peak-hold on the smoother's push count and a min/max on block time. Between them: **four integer compares, executed once per block.** Removing them recovered 172 µs — a 29 % swing that the code they contain cannot possibly account for.

    **What actually happened is placement.** Only `renderAudio()` and `loop1()` are in `.time_critical`, i.e. RAM. `ControlSmoother::Step()` — 402 bytes, called once per block — lives in XIP flash and is reached from RAM through a long-branch veneer, and so does `Engine::Process()` and the whole DSP behind it. Adding fourteen bytes to `Step()` shifted it and everything after it by ~324 bytes, and the hot path landed differently against the XIP cache. `nm` on the two images shows it plainly: `renderAudio` at `0x2000056c` both times, `Step` at `0x1000edca` (402 B) before and `0x1000ef0e` (416 B) after.

    ⚠️ **The consequence is bigger than one regression.** Coil's ~12 % headroom is not 12 % of slack, it is 12 % *at the current link order*. Any change anywhere in the image — a new console command, a longer string, a parameter added to `params.json` — can move the hot path and cost a third of the block. That also retrospectively explains "it was working fine before" moments earlier in M78f that were chased as though they were logic bugs.

    **The fix is to stop the hot path living in flash**, not to keep the image small. `.time_critical` puts a function in RAM, where placement costs nothing and there is no cache to miss; Coil has ~46 KB of SRAM free at `/4` echo, and the candidates are small — `ControlSmoother::Step()` (402 B), `ControlSmoother::apply()` (98 B), and as much of `Engine::Process()` and its callees as will fit. ⚠️ The attribute has to be `#ifdef ARDUINO`-guarded: `ControlSmoother.h` is shared with the VCV build, where `.time_critical` does not exist.

    ✅ **Done, and it bought far more than it cost.** `modules/alloycoil/include/CoilHot.h` defines `COIL_HOT(name)`, and seven functions moved out of XIP into RAM: `Engine::Process` (540 B), `EchoDelay::tick` (372), `KarplusString::ProcessInternal` (364), `ControlSmoother::Step` (402), plus `EchoDelay::Process`, `KarplusString::Process` and `ControlSmoother::apply`. **2 000 bytes of SRAM.** Verified with `nm`: all seven now sit at `0x2000xxxx` beside `renderAudio`.

    **Measured on hardware — the wireless build, radio up, at 230.4 MHz: 490 µs against a 666 µs budget, 26.9 % headroom, underruns flat.** Before the move the same build ran ~605 µs at best and wandered between 767 and 1043 µs depending on what else had changed size. The *wired* pre-session baseline was 585 µs, so the engine had been paying roughly **95 µs a block in flash fetches all along** — the XIP tax turned out to be larger than the bug that exposed it.

    The macro takes a **name** because inline and template functions are emitted into COMDAT groups and GCC refuses to put two in one named section ("causes a section type conflict") — the same reason pico-sdk's `__not_in_flash_func` takes one. `#ifdef ARDUINO`-guarded: these headers are shared with the VCV plugin, where `.time_critical` does not exist.

    ⚠️ **`ReverbSc::Process` (632 B) is still in flash**, being vendored daisysp. It is the last big per-frame function; if layout sensitivity ever returns, that is the next one to move, and the patch gets recorded in the vendor README per the re-vendoring rule.

    **The method is the other half of this entry.** Six explanations were proposed and abandoned before the right one, several resting on numbers that could not carry the weight — a `set/step` counter that sampled 1 step in 7 500, and a single block time that could not distinguish "every block is slow" from "most are fine". What actually worked was building a reference image from `HEAD` in a throwaway `git worktree` and bisecting against it: three flashes, no theories. Do that first next time, before proposing a single fix.
