- [x] 25. **STRING mode** — 4-voice vintage string ensemble; ±15¢ max spread (RELATION 0–24 st → 0–30¢ total); 3× drift multiplier (vs 1.5× CLOUD) for constant organic movement; `gChorusDepth = max(sMotion, 0.3f)` — chorus never fully stops; same hard-L/soft-L/soft-R/hard-R stereo geometry as CLOUD/CHORD; sub-octave voices with FATNESS identical to all other modes; CC 115 band 84–104

    ⚠️ **Trap, and the same one as M63b's `plugin.hpp`:** the module's `config_store.h` was silently shadowed by the platform's new one, because `-Iplatform/include` precedes `-Imodules/…`. No missing-file error — just every `AlloyConfig` field failing to resolve. Renamed to `alloy_config.h` / `audrey_config.h`, which also states ownership. **Second trap:** inserting `[env:audrey]` above `lib_deps` in `platformio.ini` silently reassigned `lib_deps` to the new env, and AlloyFlux lost `I2S` and `MIDI Library`. INI section boundaries are positional; append envs at the end.

    **Audrey's own module** is `params.json` (11 parameters, ranges/defaults/curves taken verbatim from upstream's `registerParams()`), `params.h`, `audrey_config.h`, `main.cpp`, `module_hooks.cpp`, `config_store.cpp`, `param_map.cpp` and a deliberately thin `commands.cpp` — one manifest-driven `set`/`get` pair covers every parameter and stays correct when `params.json` changes, instead of AlloyFlux's 40 hand-written commands. Engine tag `'A','U'` (0x4155). Echo max is `AUDREY_ECHO_MAX_S` in the manifest as well as the buffer, so the control cannot promise more range than the storage has. Note On sets resonator pitch; **Note Off is deliberately empty** — this is a drone instrument, and releasing a key must not stop a drone sustaining on its own feedback. ⚠️ **No panel I/O in this build**: no ADC mux, no LEDs, no buttons. Everything arrives over USB MIDI, SysEx or serial. That is the shortest path to hearing it and driving it from the web, and the I/O layer can land when there is a panel.

    **Web Configurator** is module-aware at **build time**: `activeModule.ts` reads `VITE_MODULE` and selects both the generated parameter map and the SysEx signature; `make web MODULE=audrey`. It fails closed — an AlloyFlux build simply will not connect to an Audrey module rather than showing the wrong controls. Runtime auto-detection is the better answer and the signature is already in every message, but `PARAM_MAP` is a static import throughout App.svelte and its components, so switching on the fly means making all of that reactive — a UI refactor, not worth blocking bring-up on. The generated TS map moved to `paramMapAlloyFlux.ts` and `paramMap.ts` became a hand-written shim, so no consumer changed.

    **Also fixed:** `gen_params.py` emitted `T x[] = {}` for a module with no discrete parameters — a GCC extension, not ISO C++ — now a null pointer with count 0. `commands_dispatch()` now takes the longest match, so `filter type` cannot be shadowed by `filter` depending on table order. `make audrey-host` named its sources explicitly after the glob started pulling in firmware integration files.

    ✅ **Hardware-verified — and bring-up found three things, in order of how much they mattered.**

    ⓵ **The engine does not fit at the stock clock.** Measured `690us/666us, headroom −3.6%, slow-blk climbing ~1400/s` — i.e. *every* block late, ~70 DMA underruns/sec, continuous crackle. Fixed with `board_build.f_cpu = 192000000L`. 192 MHz is chosen rather than rounded to: the I2S bit clock is 3.072 MHz and the PIO divides sysclk by a 16.8 fixed-point value, so `sysclk / 3.072 MHz` must land on a multiple of 1/256 or the sample rate drifts and every note goes flat. 150 → 48.828125 ✓, **192 → 62.5 ✓ (+28%)**, 230.4 → 75.0 ✓ (+53%), but **200 → 65.104… ✗** (~0.16% rate error ≈ 2.8 cents flat). This is the first module on the platform to need an overclock; AlloyFlux stays at 150.

    ⓶ **The engine runs hot enough to clip the DAC.** Peak 1.336 with output level already at 0.5 — ~2.5 dB over full scale — and `AudioDriver::toWire()` hard-clamps, so **0.11 % of samples (≈106/sec)** became hard discontinuities. That is a *second*, independent crackle source, distinct from the underruns, and the host harness now counts it. Fixed with a master `SoftClip` at the module's output edge in `renderAudio()` (`AUDREY_OUTPUT_SOFTCLIP`, default on) — measured 1.336 → 0.893 peak, 1056 → **0** clipped samples. Deliberately at the module edge, not inside the vendored engine, so re-vendoring stays clean. Upstream has the same headroom problem; a Daisy's codec clips it just as hard.

    ⓷ **Two controls were badly tapered**, which prompted a general platform feature: **`ParamDescriptor::skew`**, a travel exponent applied before the range, driven from `params.json` and mirrored in the web's `ccToFloat`/`floatToCC`. It complements `scale` rather than replacing it — `Log` handles multiplicative ranges but cannot be used where a range crosses zero, which is exactly the dB case. Round-trip verified exact (0 CC steps of error) for every parameter using it.
    - **`revdecay` → `skew: 0.5`.** It is a tank feedback coefficient and reverb time goes as `1/ln(fb)`, so linear gave 0.28–2.5 s over the first 80 % of travel and 2.5 s–∞ in the last 20 %. Modelled against `T60 = D·ln(0.001)/ln(fb)` with D ≈ 65 ms (mean of ReverbSc's eight tank loops at 48 kHz); now roughly geometric, ~1.3–1.4× per 10 % of travel.
    - **`echofb` → `max` 1.5 → 1.2, no skew.** The model said skew was the *wrong* tool here: everything above unity blooms to the SoftClip ceiling and sounds much the same, so the top third was already indistinguishable and skewing would have grown it to 40 %. Trimming the range instead puts unity at 83 % of travel and spreads 0–148 repeats across the first 80 % (was 0–64). ⚠️ A departure from upstream's 1.5, documented in `params.json`.
    - `fbgain` was skewed too (0.3) and then **reverted at the user's request** — the mechanism stays, inert at `skew: 1.0`, proven bit-identical to the pre-skew formula across all 128 CC values.

    **Also fixed during bring-up:** the web header now names the active module (a badge plus the browser title), and exported patches are named `<module>-patch-*.syx` rather than always `alloyflux-` — the two are not interchangeable, so that was a trap. And `App.svelte`'s per-slider hint/display overrides were keyed on **raw CC number**, so Audrey's `revdecay` (CC 92) inherited AlloyFlux's COLOR "FM depth" hint and its value formatting; now keyed on param *name* and gated on the module. That is a class of bug worth watching: CC numbers are a shared namespace across modules by design.

    ⚠️ **Still unverified: AlloyFlux itself has not been flashed since the platform extraction.** RAM is byte-identical at 356,664 B, which is strong evidence the move was pure, but its USB MIDI, SysEx and preset paths now run through `platform/src/` code that only Audrey has exercised on hardware. Flash it and round-trip a patch before trusting it.

  - [x] 63f-vcv. **Audrey VCV module + panel map + exciter input — closes M63f.** `modelAudrey` ships in the same plugin as AlloyFlux; Rack loads one DLL and offers both.

    **`VCVRackIO` promoted to `platform/vcv/`.** It was already fully positional after M63d, so it needed no change at all to serve a second module — the header just moved and its comments stopped saying "AlloyFlux". That is the M63d rename paying for itself: a HAL that names slots rather than functions is reusable by construction.

    **`modules/audrey/include/io/PanelMap.h`** maps Audrey onto the *same physical slots* AlloyFlux uses, so one PCB serves either firmware: `POT_1` is the top-left knob and `CV_7` is the FM jack whichever image is flashed, only the meaning changes. Eleven parameters against nine physical knobs, so HPF and reverb decay become SHIFT-secondaries (`POT_10`/`POT_11`) on the grounds that they are the most set-and-forget of the set.

    **`io/IOBridge.h`** — `fillAudreyParams()`, shared by firmware and plugin exactly as AlloyFlux's is, and carrying the *same curves as `params.json`*: `powf` for the log knobs, `x²` for the two `skew: 2.0` tapers, `sqrtf` for `revdecay`'s `skew: 0.5`. A knob and a MIDI CC must land on the same value or the two disagree silently.

    **The exciter input is now wired, and it is a real feature that was sitting unused.** `Engine::Process(float in, …)` sums `in` into both resonator channels ahead of the string; the firmware had been passing `0.0f`, so the string only ever self-excited from its own −90 dBFS noise floor. It is now `gExciterIn`, fed from `Cv::EXCITER` — AlloyFlux's FM jack position. ⚠️ **Bandwidth differs by platform and the difference is the point:** Rack reads the port once per sample, so patching an oscillator or noise there genuinely drives the string with audio. The firmware writes it from `readCV()` at the 128 Hz control tick, so on hardware it is a control voltage that pokes and swells the string but cannot excite it with audio. Giving it audio bandwidth needs a dedicated ADC path on the audio core; the seam is in place for it.

    **Panel is AlloyFlux's, to the third decimal.** Same 14 HP outline, same nine pot positions, same two buttons, same seven LED positions, same ten jack positions — because it is the same PCB. Only the labels change. The mapping keeps the 3×3 grid functionally coherent, which fell out of the physical layout rather than being imposed on it:

    | | left | centre | right |
    | --- | --- | --- | --- |
    | **top** — resonator + feedback | `POT_1` PITCH | `POT_2` BODY | `POT_3` FB GAIN |
    | **mid** — echo | `POT_4` SEND | `POT_5` TIME | `POT_6` FBK |
    | **low** — space + tone | `POT_7` REV DECAY | `POT_8` REV MIX ⇧VOL | `POT_9` FB LPF ⇧FB HPF |

    Slots are **row-major**, matching the panel silkscreen and `PanelLayout`'s coordinate table, so `PanelLayout::pot(Pot::PITCH)` lands on the knob the panel calls POT 1. (This table was first written with the pre-M63d numbering, where slots followed the order the parameters happened to be declared; it is corrected here because the drift is invisible until a knob is in the wrong place.) Note the *board* designators are a third numbering again — POT1/POT3/POT2 across the top — which matters only to the ADC mux driver; see `platform/vcv/PanelLayout.h`.

    Two shift pairs, both of which turned out better than my first proposal. **FB LPF / FB HPF** is the most natural pair in the set — one knob is the feedback band, shift reaches its other edge. **REV MIX / VOL** puts volume on `POT_14`, which is *the same slot AlloyFlux puts VOL on*, so SHIFT+centre-bottom means volume on both firmwares and the muscle memory carries across. (REV DECAY and REV MIX later traded places on the user's panel revision — decay left, mix centre. VOL stayed on `POT_14`: it is pinned to the *position*, not to whichever parameter shares it, which is the whole basis of the cross-firmware habit. The pair is weaker for it — two "how much" controls on one knob — and that is the right price.) FB LPF takes the knob and VOL the shift on the user's reasoning, which is the right call: sweeping the feedback filter darkens the ring audibly and is played, where output level is set once. Exposed in Rack's context menu via `SubMenuSlider`, as AlloyFlux does its six.

    **CV assignments follow the silkscreen** — each jack modulates the pot beside it, so the panel's logic survives the change of firmware: REL CV → feedback gain (the most performative CV on the module), SHP CV → echo send, MTN CV → echo feedback, SPACE CV → reverb decay, FM IN → exciter. **GATE is deliberately left unassigned**, reserved for the VCA/envelope option rather than quietly given a meaning now.

    `SubMenuSlider.hpp` moved to `platform/vcv/` alongside `VCVRackIO.h` — it is generic Rack UI, and having Audrey reach into `modules/alloyflux/vcv/` for it was exactly the cross-module include the Makefile comment warns against.

    ⚠️ **The firmware does not yet use `PanelMap.h` or `IOBridge.h`** — Audrey has no `IHardwareIO` implementation, so there is nothing to read and `gExciterIn` stays 0 there. Both are live in the VCV build and ready for the hardware I/O work.

    **Superseded first attempt** (kept because the reasoning matters): the module was first built on its own 12 HP panel with all eleven parameters as knobs. That was wrong for the same reason the positional HAL exists — Audrey shares AlloyFlux's hardware, so it does not get its own layout, it gets AlloyFlux's with different names.

    Master soft clip applied in `process()` too, matching the firmware's output edge.

    ⚠️ **Build trap recorded in the Makefile:** unlike the firmware, the plugin hosts *all* modules in one binary, so every module's include root is on the path at once — and both modules ship a `params.h` and an `io/PanelMap.h`. A shared `-I` list would hand one module the other's globals with no diagnostic until link time. Include roots are therefore applied **per object** (`ALLOYFLUX_INC` / `AUDREY_INC`), not globally. Module-specific headers are named for their module (`alloy_config.h`, `audrey_config.h`) for the same reason.

  - [x] 63f-ab. **The echo A/B — both M63f DSP risks measured and discharged.** `make audrey-ab` / `make audrey-ab-sweep`, source in `modules/audrey/test/echo_ab.cpp`. Done as an offline harness with an inline FFT rather than a swept sine into Rack's spectrum analyser: the answer wanted is a number that can be re-checked in a minute and can gate a later change, not an impression. It drives `EchoDelay` directly — no string, no reverb, no feedback loop — so nothing else can colour the result, and it takes `AUDREY_ECHO_MAX_S` from the engine header so the buffer under test is the size the firmware actually builds.

    A switch was added for the measurement: **`AUDREY_ECHO_ANTIALIAS`**, purely so the filter can be compared against its own absence. Turning it off in a shipping build is not a trade-off, it is a bug, and the header says so.

    **Risk 1 — fold-down. The anti-alias filter works and is load-bearing.** Fold-down level for a 0 dBFS input, filter off → on: 7 kHz→5 kHz −30.5→−49.9 dB; 9 kHz→3 kHz −15.1→−44.9; **11 kHz→1 kHz −3.1→−41.1**; 13 kHz→1 kHz −3.1→−50.2; 17 kHz→5 kHz −30.5→−99.0. Without it the fold-down is as loud as the input, at 1 kHz, exactly where the loop's 800 Hz bandpass passes it through untouched — the risk was entirely real.

    **A second artifact turned up that the filter cannot touch, and it would have been easy to misread as a failure of the first:** *reconstruction imaging* from the linear interpolator on the way back up. A 5 kHz input produces a 7 kHz image (12000 − 5000) at −43 dB, against −71 dB for the same spur in the ÷1 reference build. Not aliasing, not fixable by an input filter; would need a better reconstruction filter. At −43 dB in a tape-ish echo it reads as character. Measured rather than assumed, which is the difference that matters.

    **Risk 2 — quantiser noise. int16 costs 0.0–0.1 dB and is therefore free.** SNR with a −40 dBFS tone circulating at 0.95 feedback: ÷1 float 38.1 dB, ÷4 float 37.6, ÷4 int16 37.6. The floor is set by `SoftClip`'s intermodulation inside the loop, not by the quantiser. With over-unity feedback and true silence in, output is bit-exact zero in every build — **the quantiser does not bootstrap itself.** That is the 8× memory reduction vindicated: 750.2 KiB → 93.9 KiB per channel for no audible cost, which is the whole reason Audrey fits at all.

    **Two changes fell out of the numbers, both applied:**

    - **`AUDREY_ECHO_NOISE_SHAPE` default 1 → 0.** Error feedback is the textbook improvement on a quantiser and it bought nothing here (37.5 vs 37.6 dB). What it cost was silence: the error term keeps the quantiser dithering around zero, leaving a permanent −118.9 dBFS floor where plain truncation decays to bit-exact zero. Inaudible alone — but this echo allows feedback past unity, which amplifies that floor at ~1.7 dB/s. Trading a measurable "never truly silent" for an unmeasurable improvement is the wrong way round.
    - **Anti-alias cutoff 0.35 → 0.25 × the decimated rate** (4200 → 3000 Hz). Another 12 dB of rejection: the 11 kHz worst case went −41.1 → **−53.2 dB**, 13 kHz → −62.3. Nearly free, because the loop's own bandpass is at 800 Hz / 12 dB/oct and has already taken 23 dB out by 3 kHz — there is very little real echo content in the band given away. SNR unchanged at 37.6 dB.

    ⚠️ **One measurement trap, recorded because it produced a confusing result first:** a single-sample impulse is a useless stimulus for a decimated path. The decimator only samples every kDecim-th frame, so a one-sample impulse is simply never seen — three times out of four at ÷4. With the anti-alias filter on it smears across enough samples to get through, so the impulse "works"; with the filter off it vanishes entirely and the echo reads as silent. The harness primes with a 10 ms raised-cosine burst instead, which survives both.

  - [x] 63f. **Audrey module at 48 kHz + VCV voicing** — second build env; **Audrey runs at 48 kHz, not 32768** — this is the whole answer to avoiding artifacts. At 32768 its `FeedbackLPFCutoff` (range 100–18000, default **18000**) sits above the 16384 Hz Nyquist where `BiquadCascade::SetCutoff` clamps to exactly `sr/2` and the bilinear prewarp diverges — degenerate _at boot_; two waveshapers (`Overdrive` in the resonator loop, `SoftClip` in the echo loop) fold aliasing 32% lower and regenerate it each pass because both sit _inside_ feedback paths; and the string/reverb one-pole coefficients would need re-tuning by ear. At 48 kHz none of this happens. Memory: `reverbsc.h` declares `float aux_[98936]` = **386 KiB as a single member** and must be resized to 25,600 floats; echo decimated ÷4 to 12 kHz and stored as `int16` (234 KiB); engine total ~414 KiB, leaving ~56 KiB after platform infrastructure — lever if it bites is a 4.0 s max echo instead of 5.0 s. Two genuinely new DSP risks, both answerable in VCV before touching hardware: the **mandatory anti-alias LPF** on the echo send (the tap is post-reverb and full-bandwidth — verify with a swept sine and spectrum analyser) and **Q15 quantization noise** regenerating at feedback > 1.0 (clamp hard to ±0.999 before quantizing since `SoftClip` can exceed unity; convert to float _then_ interpolate; optional first-order error-feedback noise shaping). Expose ÷3/÷4 and float@48k/Q15@12k as compile-time switches and A/B them live.
  - [x] 63g. **Firmware bring-up + measurement** — `arm-none-eabi-size` against the margin; cycle-count `Engine::Process` over 1000 samples; long-run at max feedback gain and echo feedback > 1.0 for 10 minutes confirming no denormals, NaNs or DC drift. **Open decision — does AlloyFlux move to 48 kHz too?** For: the engine is already rate-parametric (`init(audioRate, controlRate)`, `setSampleRate()`) and runs at host rate in VCV daily, so hardware would finally match the plugin; it also fixes `gFilterCutoff` maxing at 16000 Hz against a 16384 Hz Nyquist (97.6%, near-degenerate for the SVF and ladder). Hardware and the VCV build now run at the same rate, and `gFilterCutoff`'s 16000 Hz maximum is off the Nyquist it used to sit at.
